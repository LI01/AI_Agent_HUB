Write tests that would fail against the codebase as it was before the change and pass against it now — the test is the proof the change did something. Cover the boundaries explicitly: empty input, max size, off-by-one, null/missing fields, duplicate keys, wrong type, concurrent access, and the error paths the code claims to handle. Each test gets one assertion of intent, a name that describes the behavior under test (not the function), and arrange/act/assert separated by blank lines. Don't test the language or the framework; don't write a "smoke test" if a real assertion is possible. If you can't construct a failing-then-passing pair for a claim, say which claim and why.
